## 一、评估指标体系

### 1.1 指标总览

| 优先级 | 指标名称 | 自动/半自动 | 计算复杂度 | 评估对象 |
|--------|----------|-------------|------------|----------|
| **P0** | 硬约束满足率（CSR） | 全自动 | 低 | 系统输出 |
| **P0** | 候选召回命中率（Hit@K） | 全自动 | 低 | 检索结果 |
| **P0** | 参数事实准确率（PFA） | 半自动（规则+人工抽检） | 中 | 生成文本 |
| **P0** | 推荐理由证据支持率（ESR） | 半自动（规则+人工抽检） | 中 | 生成文本 |
| **P1** | 排序质量（MRR / NDCG@K） | 全自动 | 中 | 排序结果 |
| **P1** | 意图分类准确率 | 全自动 | 低 | 意图识别 |
| **P1** | 追问触发准确率 | 全自动 | 低 | 追问判断 |
| **P2** | 冲突检测准确率 | 全自动 | 低 | 冲突处理 |
| **P2** | 回复自然度评分 | 人工 | 高 | 生成文本 |
| **P2** | 整体用户满意度 | 人工 | 高 | 端到端体验 |

**P0 为必须完成指标，P1 为尽力完成，P2 为可选加分项。**

### 1.2 P0 核心指标详解

#### 1.2.1 硬约束满足率（Constraint Satisfaction Rate, CSR）

**定义**：系统推荐的商品中，满足用户所有硬约束的商品比例。

**计算公式**：
```
CSR = (满足全部硬约束的推荐商品数) / (总推荐商品数)

对于单次查询 q：
csr(q) = count({sku ∈ recommended_skus(q) | check_all_constraints(sku, constraints(q)) == True}) / |recommended_skus(q)|

系统整体 CSR = mean(csr(q) for q in test_queries)
```

**计算方式**：全自动
- 输入：推荐 SKU 列表 + 用户硬约束
- 检查：逐项比较结构化字段
- 输出：通过/失败（布尔值）

**示例**：
```
用户约束：budget_max=8000, gpu_required=true, ram_min=16
系统推荐：5 款商品
其中 4 款满足全部约束，1 款违反 budget_max（价格 8299）
CSR = 4/5 = 0.80
```

**为什么重要**：这是区分"Agent"和"普通聊天机器人"的关键指标。普通 RAG 可能推荐违反约束的商品，而 Agent 必须保证约束满足。

---

#### 1.2.2 候选召回命中率（Hit@K）

**定义**：系统推荐的 Top-K 商品中，命中人工标注的"允许商品集合"的比例。

**计算公式**：
```
Hit@K = |recommended_topK ∩ allowed_skus| / |allowed_skus|

其中：
- recommended_topK：系统推荐的 Top-K 商品（K=5）
- allowed_skus：人工标注的该查询下应该被推荐的商品集合

如果 allowed_skus 为空（无完全满足商品），则 Hit@K = 不适用，改用冲突处理评估指标
```

**计算方式**：全自动
- 输入：系统推荐 Top-5 + 人工标注 allowed_skus
- 检查：集合交集
- 输出：命中率（0–1）

**示例**：
```
allowed_skus = [sku_A, sku_B, sku_C, sku_D]  # 4 款应该推荐
系统推荐 Top-5 = [sku_A, sku_C, sku_E, sku_F, sku_B]
命中 = {sku_A, sku_B, sku_C}，共 3 款
Hit@5 = 3/4 = 0.75
```

**Hit@K 与 Recall@K 的区别**：
- Hit@K 检查"推荐列表是否包含了应该推荐的商品"
- 不要求推荐列表只包含允许商品（允许包含额外商品，只要这些商品也满足约束）
- 因此 Hit@K 与 CSR 互补：CSR 检查"推荐的商品是否都合法"，Hit@K 检查"合法商品是否被推荐"

---

#### 1.2.3 参数事实准确率（Parameter Factual Accuracy, PFA）

**定义**：系统生成的推荐理由中，引用的商品参数与知识库一致的比例。

**计算方式**：半自动（规则提取 + 人工抽检）

**步骤**：
```
1. 从推荐理由文本中提取参数声明
   使用规则：匹配"搭载XX"、"配备XX"、"XX内存"、"XX显卡"等模式
   
2. 将提取的参数与 products.jsonl 中对应 SKU 的字段比对
   例如：文本说"搭载 i7-14650HX" → 检查 sku.cpu_model 是否为 "i7-14650HX"
   
3. 计算准确率：
   PFA = (匹配正确的参数声明数) / (总提取的参数声明数)
```

**抽检策略**（控制工作量）：
- 每轮测试随机抽取 30% 的推荐结果进行人工复核
- 如果规则提取的准确率低于 90%，则扩大抽检比例到 50%
- 如果连续 3 轮抽检准确率 > 95%，则降低抽检比例到 20%

**示例**：
```
推荐理由："为您推荐联想拯救者Y7000P，搭载 i7-14650HX 处理器和 RTX 4060 显卡，
配备 32GB 内存，重量仅 2.55kg，售价 7999 元。"

提取参数声明：
1. "i7-14650HX" → cpu_model 匹配 ✓
2. "RTX 4060" → gpu_model 匹配 ✓
3. "32GB 内存" → ram_gb=32 匹配 ✓
4. "2.55kg" → weight_kg=2.55 匹配 ✓
5. "7999 元" → price=7999 匹配 ✓

PFA = 5/5 = 1.0
```

**为什么重要**：面试时最常问的问题之一——"你怎么保证推荐内容中的参数是对的？"PFA 提供了量化答案。

#### 1.2.4 推荐理由证据支持率（Evidence Support Rate, ESR）

**定义**：推荐理由中的每个论点，都有对应的事实证据或文本证据支持的比例。

**计算方式**：半自动（规则匹配 + 人工抽检）

**步骤**：
```
1. 将推荐理由拆分为独立论点
   例如："性能强劲"、"适合编程"、"屏幕素质优秀"、"性价比高"
   
2. 检查每个论点是否有证据支持：
   - 事实证据：products.jsonl 中的结构化参数可以直接支撑
     例如："32GB 内存" → ram_gb=32（事实证据）
   - 文本证据：documents.jsonl 中的 evidence 类型文档可以支撑
     例如："适合编程" → 某评测说"编程场景编译速度快"（文本证据）
   
3. 计算支持率：
   ESR = (有证据支持的论点数) / (总论点数)
```

**判断规则**（简化版）：
- 参数类论点（"32GB 内存"、"RTX 4060"）→ 检查结构化字段匹配 → 自动判定
- 场景类论点（"适合编程"、"游戏性能优秀"）→ 检查是否有对应的 evidence 文档 → 规则匹配
- 主观评价类论点（"性价比高"、"外观精美"）→ 较难自动判定，需人工抽检

**抽检策略**：
- 主观评价类论点 100% 人工抽检
- 参数类和场景类论点 30% 抽检

**示例**：
```
推荐理由论点拆解：
1. "性能强劲，适合编程和游戏" → 有证据：评测文档（"多线程编译速度优秀"） ✓
2. "32GB 大内存满足开发需求" → 有证据：fact（ram_gb=32） ✓
3. "屏幕素质优秀" → 有证据：评测文档（"2560x1600 高色域屏"） ✓
4. "机身较重" → 有证据：fact（weight_kg=2.55） ✓
5. "性价比高" → 需要价格/性能对比 → 检查是否有价值评估证据 → 人工判定 ✓

ESR = 5/5 = 1.0
```

**为什么重要**：这是 RAG 系统的核心优势——推荐有证据支撑，而不是大模型幻觉。ESR 量化了这一优势。

### 1.3 P1 辅助指标详解

#### 1.3.1 MRR（Mean Reciprocal Rank）

**定义**：系统推荐列表中，第一个命中允许集合的商品的排名倒数。

```
MRR = mean(1 / rank_of_first_hit(q) for q in test_queries)

其中 rank_of_first_hit 是第一个 allowed_sku 在推荐列表中的位置
如果 Top-K 中没有命中，则 MRR = 0
```

**示例**：
```
allowed_skus = [sku_B, sku_C]
推荐列表 = [sku_A, sku_B, sku_D, sku_E, sku_C]
第一个命中是 sku_B，排名 = 2
1/rank = 1/2 = 0.5
```

#### 1.3.2 NDCG@K（Normalized Discounted Cumulative Gain）

**定义**：考虑排序位置的加权命中率，排名越靠前权重越高。

```
DCG@K = Σ(relevance(i) / log2(i + 1)) for i = 1 to K

其中 relevance(i) = 1 if recommended[i] ∈ allowed_skus else 0

NDCG@K = DCG@K / IDCG@K

IDCG@K 是理想排序下的 DCG（即所有 allowed_skus 都排在最前面）
```

**为什么使用 MRR/NDCG**：
- Hit@K 只关心"有没有命中"，不关心"排在哪里"
- MRR 和 NDCG 评估排序质量：好的系统应该把最相关的商品排在前面

#### 1.3.3 意图分类准确率

```
Intent_Accuracy = (正确分类的查询数) / (总查询数)
```

**多模态查询分类**：上传截图后路由到正确意图的比例。

#### 1.3.4 追问触发准确率

```
分为两个子指标：

Precision = (正确触发的追问数) / (总触发追问数)
Recall = (正确触发的追问数) / (应该触发追问的总数)

F1 = 2 × Precision × Recall / (Precision + Recall)
```

**判定标准**：
- 正确触发：查询确实信息不足，追问后获得了有价值的新信息
- 错误触发：查询信息已充足，但系统仍追问；或查询信息不足但系统未追问

### 1.4 P2 可选指标

#### 1.4.1 回复自然度评分

**方式**：人工对 20 条系统输出打分（1–5 分）
**维度**：语言流畅度、逻辑清晰度、专业度、说服力
**工作量**：约 2 小时

#### 1.4.2 整体用户满意度

**方式**：请 3–5 位同学作为测试用户，每人完成 10 条查询后打分
**维度**：结果相关性、推荐质量、交互体验、信任度
**工作量**：约 1 天（含招募和测试）

- 每类 2–4 条，覆盖主要场景
- 用于调试约束提取、过滤逻辑、排序算法

### 2.3 测试查询设计方法

**批量生成 + 人工核验**：

```
步骤 1：基于商品知识库半自动生成查询
  └── 遍历商品参数组合，生成自然语言查询模板
  └── 例如：{brand} + {category} + {budget} + {ram}
  └── 填充具体值："联想游戏本，预算8000，内存32G"

步骤 2：人工改写为自然表达
  └── 将模板改写成真实用户的说话方式
  └── 例如："想买台联想拯救者那种游戏本，预算别超8000，最好32G内存"

步骤 3：标注期望结果
  └── 人工标注：允许商品集合、禁止商品、是否应追问、是否无完全满足

步骤 4：交叉核验
  └── 另一位标注者检查，不一致时讨论决定
```

### 2.4 标注字段定义

每条测试查询必须标注以下字段：

```json
{
  "query_id": "test_001",
  "query_type": "normal_purchase",
  "natural_language": "想买台笔记本写代码，预算7000左右",
  "hard_constraints": {
    "budget_max": 7000,
    "scenarios": ["编程开发"]
  },
  "soft_preferences": {
    "performance": "medium",
    "portability": "medium"
  },
  "allowed_skus": ["sku_001", "sku_015", "sku_023", "sku_031"],
  "forbidden_skus": ["sku_002"],
  "should_ask_followup": false,
  "no_exact_match": false,
  "annotator": " annotator_A",
  "annotation_date": "2026-08-01",
  "notes": "允许 SKU 基于预算和场景筛选，sku_002 因价格过高被排除"
}
```

### 2.5 标注原则（避免依赖系统派生结论）

**必须基于以下信息标注**：
- ✅ `products.jsonl` 中的结构化参数
- ✅ `documents.jsonl` 中 `type=fact` 的客观事实
- ✅ 标注者本人的产品知识和判断

**禁止基于以下信息标注**：
- ❌ 系统生成的 `scenario_desc`、`pros_summary` 等派生总结
- ❌ 系统生成的推荐理由
- ❌ 其他模型的推荐结果

**标注流程**：
1. 标注者阅读查询，理解用户需求
2. 标注者独立浏览 `products.jsonl`，筛选符合条件的商品
3. 标注者记录允许和禁止的商品列表
4. 另一位标注者独立重复步骤 2–3
5. 对比两位标注者的结果，计算标注一致性（Inter-Annotator Agreement）
6. 不一致时讨论达成一致，记录分歧原因

### 2.6 标注一致性指标

```
IAA (Inter-Annotator Agreement) = |A ∩ B| / |A ∪ B|

其中 A 和 B 是两位标注者的允许 SKU 集合

目标：IAA > 0.85（高一致性）
如果 IAA < 0.70，说明查询设计模糊，需要修改查询或增加标注规范
```

## 三、消融实验与对比基线设计

### 3.1 实验目标

通过消融实验分别验证以下模块的独立贡献：
1. **结构化约束过滤**：是否比纯语义检索更能保证约束满足？
2. **混合检索**：结构化过滤 + 向量检索是否比单一检索更好？
3. **场景化排序**：场景化权重是否比统一排序更贴合用户需求？
4. **澄清机制**：追问是否提升了推荐质量？
5. **结果校验**：verify_response 是否减少了参数错误？

### 3.2 四个对比基线

| 基线 | 名称 | 说明 | 目的 |
|------|------|------|------|
| **基线 A** | 纯向量检索（Pure RAG） | 仅使用向量相似度检索，无结构化过滤，无约束提取 | 验证结构化约束的价值 |
| **基线 B** | 混合检索（Hybrid Retrieval） | 向量检索 + BM25 关键词匹配，无结构化约束过滤 | 验证混合检索的价值 |
| **基线 C** | 混合检索 + 结构化约束（Hybrid + Constraint） | 基线 B + 结构化硬约束过滤 + 软偏好排序 | 验证约束过滤和排序的价值 |
| **基线 D** | 完整 Agent（Full Agent） | 基线 C + 意图识别 + 澄清机制 + 场景化排序 + 冲突处理 + 结果校验 | 验证完整 Agent 流程的价值 |

### 3.3 消融实验设计

**实验 1：结构化约束的价值**
```
对比：基线 A vs 基线 C
指标：CSR、Hit@5
预期：基线 C 的 CSR 显著高于基线 A（证明约束过滤有效）
```

**实验 2：混合检索的价值**
```
对比：基线 A vs 基线 B
指标：Hit@5、MRR
预期：基线 B 的 Hit@5 高于基线 A（证明关键词+语义混合更好）
```

**实验 3：场景化排序的价值**
```
对比：基线 C（固定权重）vs 基线 D（场景化权重）
指标：MRR、NDCG@5
预期：基线 D 的 MRR 高于基线 C（证明场景化排序更贴合需求）
```

**实验 4：澄清机制的价值**
```
对比：基线 C（无追问）vs 基线 D（有追问）
数据集：仅使用模糊需求查询（8 条）
指标：追问触发后 Hit@5 的提升幅度
预期：追问后推荐质量提升（信息更充分）
```

**实验 5：结果校验的价值**
```
对比：基线 D（无校验）vs 基线 D（有校验）
指标：PFA、ESR
预期：校验后 PFA 和 ESR 提高（减少了参数错误和幻觉）
```

### 3.4 实验可复现性保障

| 保障措施 | 说明 |
|----------|------|
| **固定随机种子** | 所有随机操作（如抽检、排序 tie-breaking）使用固定种子 |
| **固定模型版本** | Embedding 模型、LLM 版本在实验中保持一致 |
| **固定超参数** | 排序权重、Top-K 值、阈值在实验中保持一致 |
| **公开测试集** | 正式测试集标注公开，其他研究者可复现 |
| **代码开源** | 实验脚本开源，消融实验可一键运行 |

## 五、风险控制与兜底方案

### 5.1 风险 1：测试集泄露

**风险**：开发过程中使用正式测试集调试，导致过拟合。

**对策**：
- 正式测试集在开发阶段**严格隔离**
- 开发集用于调试，正式测试集仅用于最终评估
- 基线实验先在开发集上验证流程，再跑正式集

### 5.2 风险 2：标注不一致

**风险**：两位标注者对"允许 SKU"的理解不同，导致 IAA 低。

**对策**：
- 制定详细的标注规范（如"预算±10% 内可接受"、"独显要求不可妥协"）
- 先标注 10 条查询，计算 IAA，如果 < 0.70 则完善规范后再继续
- 对争议查询引入第三位标注者仲裁

### 5.3 风险 3：LLM 输出不稳定

**风险**：LLM 生成的推荐理由每次运行结果不同，导致指标波动。

**对策**：
- 固定 LLM 版本和参数（temperature=0）
- 每个查询运行 3 次，取平均指标
- 记录标准差，如果标准差 > 0.05，增加运行次数到 5 次

### 5.4 风险 4：计算资源不足

**风险**：Embedding 计算、多次 LLM 调用耗时过长。

**对策**：
- 使用轻量级 Embedding 模型（如 BGE-small）
- 消融实验中，基线 A 和 B 不需要 LLM 调用（纯检索）
- 提前预计算所有商品的 Embedding，避免重复编码
