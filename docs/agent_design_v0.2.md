# 约束推理与 Agent 分支设计 v0.2

**项目名称**：基于多模态 RAG 与约束推理的电商智能导购 Agent
**设计原则**：结构化硬约束 + 语义软偏好 + 轻量 Agent 分支
**适用范围**：第一版笔记本电脑品类
**更新日期**：2026-08-01

---

## 一、核心设计思想

### 1.1 为什么是 Agent，而不仅是 RAG 问答

| 维度 | 普通 RAG 问答 | 本系统（Agent） |
|------|-------------|----------------|
| **输入处理** | 接收查询 → 直接检索 | 接收查询 → **意图识别** → 判断是否需要追问 → 选择工具 |
| **状态管理** | 无状态，每次独立 | **维护用户需求状态**，支持多轮更新和冲突检测 |
| **约束处理** | 靠语义相似度隐式匹配 | **显式提取结构化约束**，先做硬过滤再做软排序 |
| **冲突处理** | 无法识别冲突，可能推荐违规商品 | **检测约束冲突**，主动解释并引导用户决策 |
| **工具调用** | 单一检索 | **多工具动态调用**：解析 → 提取 → 过滤 → 检索 → 排序 → 校验 |
| **输出控制** | 直接生成回答 | **分阶段校验**：过滤结果校验 → 参数事实校验 → 推荐理由证据校验 |
| **会话能力** | 单轮 | **多轮对话**，能追问、澄清、更新需求、处理冲突 |

### 1.2 Agent 工作流总览

```
用户输入（文本或图片）
  → [意图识别与路由] → 确定用户要做什么
    ├─ 购买咨询 → 进入约束提取流程
    ├─ 商品对比 → 直接进入对比分析
    ├─ 单商品询问 → 直接进入单商品问答
    ├─ 上传截图 → 先解析图片，再路由
    └─ 模糊需求 → 触发追问

购买咨询路径：
  → [需求解析] → 提取硬约束 + 软偏好
    ├─ 信息不足 → [追问分支] → 追问关键信息 → 等待用户回复 → 更新状态
    └─ 信息充足 → 继续
  
  → [硬约束过滤] → 从知识库中剔除不满足商品
    ├─ 结果为空 → [冲突处理分支] → 分析冲突约束 → 建议放宽 → 等待用户决策
    └─ 有候选 → 继续
  
  → [软偏好排序] → 对候选商品做多维度评分
  → [检索增强] → RAG 检索相关文本证据
  → [推荐理由生成] → 基于证据生成个性化建议
  → [结果校验] → 检查约束满足率 + 参数准确性 + 证据忠实度
  → [流式输出] → 逐步呈现：意图确认 → 候选列表 → 对比分析 → 最终建议
```

## 二、意图识别与路由

### 2.1 意图类型定义（第一版）

| 意图类型 | 标识 | 触发特征 | 处理分支 |
|----------|------|----------|----------|
| **购买咨询** | `purchase` | 含预算、用途、需求描述 | 主流程：提取约束 → 过滤 → 排序 → 推荐 |
| **商品对比** | `compare` | 明确提及 2+ 商品名称 | 对比分支：提取对比维度 → 多商品参数对齐 → 差异分析 |
| **单商品询问** | `inquiry` | 提及 1 款商品 + 疑问词 | 单商品问答：参数解释 → 适用场景分析 |
| **截图解析** | `multimodal` | 上传图片 | 图片解析 → 参数提取 → 匹配 SKU → 路由到 purchase/compare/inquiry |
| **需求澄清** | `clarify` | 对追问的回复 | 更新需求状态 → 重新进入主流程 |
| **冲突决策** | `resolve` | 对冲突提示的回复 | 更新约束（放宽某项） → 重新过滤 |

### 2.2 意图识别方式

使用**规则 + LLM 分类**两层机制：

1. **规则层**（快速判断）：
   - 含"vs/对比/比较/哪个好" → `compare`
   - 含"怎么样/值得买吗/优缺点"且只提及1款 → `inquiry`
   - 含"推荐/想买/求建议" → `purchase`
   - 含图片输入 → `multimodal`

2. **LLM 层**（兜底确认）：
   - 规则层无法确定时，调用轻量分类 prompt
   - 输入：用户查询 + 历史上下文（如果有）
   - 输出：意图类型 + 置信度

### 2.3 路由决策逻辑

```
if 当前会话状态为 "等待追问回复":
  → 意图 = clarify → 更新需求状态 → 重新评估是否充足

else if 用户上传图片:
  → 意图 = multimodal → 解析图片 → 提取参数 → 匹配 SKU
  → if 匹配到1款: 路由到 inquiry
  → if 匹配到2+款: 路由到 compare 或 purchase
  → if 未匹配: 询问用户是否想按参数搜索

else if 查询含对比信号 and 提取到2+商品名:
  → 意图 = compare

else if 查询含1款商品名 and 疑问信号:
  → 意图 = inquiry

else:
  → 意图 = purchase（默认）
  → 检查需求信息充足度
    → 不足: 触发追问
    → 充足: 进入约束提取
```

## 三、需求解析与状态管理

### 3.1 需求状态结构

每个会话维护一个 `UserNeedState` 对象：

```json
{
  "session_id": "sess_20260801_001",
  "intent": "purchase",
  "need_completeness": "partial",
  
  "hard_constraints": {
    "budget_max": 8000,
    "budget_min": null,
    "gpu_required": true,
    "ram_min": 16,
    "weight_max": 2.0,
    "screen_size_range": [14.0, 16.0]
  },
  
  "soft_preferences": {
    "performance": 0.8,
    "portability": 0.9,
    "battery_life": 0.6,
    "value_for_money": 0.7,
    "brand": ["联想", "华硕"],
    "scenarios": ["编程开发", "移动办公"]
  },
  
  "extracted_entities": {
    "mentioned_products": ["拯救者Y7000P"],
    "mentioned_brands": ["联想"],
    "mentioned_specs": ["32GB内存"]
  },
  
  "missing_critical_info": ["预算", "是否需要独显"],
  
  "history": [
    {
      "turn": 1,
      "user_input": "我想买台笔记本",
      "agent_action": "ask_followup",
      "agent_message": "您的预算大概是多少？主要用来做什么？"
    }
  ],
  
  "pending_action": "wait_for_user_response",
  "last_updated": "2026-08-01T09:30:00"
}
```

### 3.2 硬约束字段定义

| 约束名 | 数据类型 | 提取规则 | 过滤逻辑 |
|--------|----------|----------|----------|
| `budget_max` | int/None | "预算X以内/不超过X" | price <= budget_max |
| `budget_min` | int/None | "预算X以上/至少X" | price >= budget_min |
| `gpu_required` | bool/None | "必须独显/要带显卡" | gpu_type == "独立显卡" |
| `ram_min` | int/None | "内存至少X/不低于X" | ram_gb >= ram_min |
| `weight_max` | float/None | "重量不超过X/轻于X" | weight_kg <= weight_max |
| `screen_size_range` | [float, float]/None | "X寸到Y寸/大屏/小屏" | screen_size 在范围内 |
| `cpu_brand` | string/None | "要Intel/AMD/苹果" | cpu_brand 匹配 |
| `category` | string/None | "游戏本/轻薄本/全能本" | product_category 匹配 |

### 3.3 软偏好字段定义

| 偏好名 | 类型 | 取值范围 | 说明 |
|--------|------|----------|------|
| `performance` | float | 0.0–1.0 | 性能重视程度（影响 CPU/GPU 评分权重） |
| `portability` | float | 0.0–1.0 | 便携重视程度（影响 weight_kg 评分权重） |
| `battery_life` | float | 0.0–1.0 | 续航重视程度（影响 battery_wh 评分权重） |
| `value_for_money` | float | 0.0–1.0 | 性价比重视程度（影响 price 评分权重） |
| `brand` | list[string] | 品牌名称列表 | 品牌偏好（匹配加分） |
| `scenarios` | list[string] | 场景描述 | 场景匹配（语义相似度） |

### 3.4 自然语言提取规则

使用 **LLM + 规则校验** 两层提取：

**第一层：LLM 提取**
- Prompt 模板要求 LLM 从用户查询中提取硬约束和软偏好
- 输出 JSON 格式，严格限定字段
- 对于模糊表达（如"轻便"），映射为 weight_max < 1.5
- 对于"编程""剪辑"等场景词，映射到 scenario_desc 语义匹配

**第二层：规则校验**
- 检查提取值是否在合理范围（如预算 0–50000 元）
- 检查约束之间是否已有冲突（如预算 < 3000 且 必须独显）
- 不通过校验的约束标记为 `needs_confirmation`

## 四、硬约束过滤系统

### 4.1 过滤流程

```
候选商品池（36–48款）
  → 预算上限过滤（如果有 budget_max）
  → 预算下限过滤（如果有 budget_min）
  → 内存下限过滤（如果有 ram_min）
  → 重量上限过滤（如果有 weight_max）
  → 独显要求过滤（如果 gpu_required == true）
  → 屏幕尺寸范围过滤（如果有 screen_size_range）
  → CPU 品牌过滤（如果有 cpu_brand）
  → 品类过滤（如果有 category）
  → 得到过滤后候选集
```

### 4.2 边界情况处理

| 情况 | 处理策略 |
|------|----------|
| 某约束字段值为 null | 不应用该约束过滤 |
| 用户说"越便宜越好" | budget_max = null，budget_min 可能为某个最低值或也为 null |
| 用户说"性价比" | 不设置 budget_max，但提升 value_for_money 偏好权重 |
| 用户说"轻薄" | weight_max = 1.5，同时提升 portability 偏好权重 |
| 用户同时说"大屏"和"便携" | screen_size_range 可能为空（无法量化），依赖后续语义排序 |

### 4.3 过滤结果状态

| 结果 | 数量 | 处理 |
|------|------|------|
| 完全满足 | >= 3 款 | 正常进入排序 |
| 完全满足 | 1–2 款 | 正常进入排序，但可能在推荐理由中说明"选择较少" |
| 完全满足 | 0 款 | 触发冲突处理分支 |

## 五、软偏好排序系统

### 5.1 评分维度

每款通过硬过滤的商品，计算以下维度得分：

| 维度 | 计算方式 | 权重影响因素 |
|------|----------|-------------|
| **性能分** | 基于 cpu_cores + gpu_vram_gb + ram_gb 归一化 | `performance` 偏好 |
| **便携分** | 基于 weight_kg 反向归一化（越轻分越高） | `portability` 偏好 |
| **续航分** | 基于 battery_wh 归一化 | `battery_life` 偏好 |
| **性价比分** | 基于性能/price 比值 | `value_for_money` 偏好 |
| **品牌匹配分** | 0/1（是否在 brand 列表中） | `brand` 偏好 |
| **场景语义分** | 基于 scenario_desc 与用户需求场景的 embedding 相似度 | `scenarios` 偏好 |

### 5.2 融合排序公式

```
总评分 = Σ(维度得分 × 维度权重 × 用户偏好权重)

其中：
- 维度权重：系统预设（如性能0.25、便携0.20、续航0.15、性价比0.20、品牌0.10、场景0.10）
- 用户偏好权重：从 soft_preferences 读取（如 performance=0.8）

如果用户未显式表达某偏好，默认权重为 0.5（中性）
```

### 5.3 排序结果

按总评分降序排列，默认取 Top-5 进入推荐理由生成环节。

## 六、追问机制

### 6.1 何时追问

触发条件（满足任一）：

1. **关键约束缺失**：缺少预算 且 缺少使用场景/用途
2. **约束过于宽泛**：只有品类要求（如"推荐游戏本"），无预算、无性能要求
3. **冲突已存在但未识别**：用户说"要轻薄游戏本"，系统需要确认重量上限
4. **首次会话且无历史**：用户只说"想买笔记本"

**不追问的情况**：
- 用户已提供预算 + 至少一个使用场景/需求
- 用户明确指定了具体商品（进入对比/询问流程）
- 用户上传了截图（系统可以从截图提取参数）
- 追问次数已达上限

### 6.2 追问什么（优先级）

| 优先级 | 追问内容 | 理由 |
|--------|----------|------|
| 1 | 预算范围 | 影响过滤和排序，最重要 |
| 2 | 主要用途/场景 | 影响场景语义匹配和品类判断 |
| 3 | 是否需要独立显卡 | 显著缩小候选范围 |
| 4 | 重量要求 | 区分轻薄本和游戏本的关键 |
| 5 | 内存需求 | 影响编程/开发场景 |

### 6.3 追问策略

**第一版限制**：
- 最多追问 **1 次**
- 追问时一次最多问 **2 个问题**（避免用户反感）
- 追问内容基于缺失信息的优先级自动生成

**追问模板示例**：

```
用户输入："我想买台笔记本"
Agent 追问："好的！为了给您更精准的推荐，想先确认两点：
1. 您的预算大概在什么范围？
2. 主要用来做什么（比如办公、编程、游戏、设计）？"
```

```
用户输入："推荐个游戏本，预算8000"
Agent 不追问：直接进入约束提取（已有预算和品类）
```

### 6.4 追问后的状态更新

用户回复追问后：
1. 解析回复，提取新的约束和偏好
2. 合并到现有 UserNeedState
3. 标记 `need_completeness` 为 `sufficient` 或继续 `partial`
4. 如果仍然不足但已达追问上限，进入主流程（用现有信息尽力推荐）

## 七、冲突处理机制

### 7.1 冲突检测

当硬约束过滤后结果为 0 款时，触发冲突分析：

```
分析每个约束的"严格程度"：
  - budget_max: 宽松度 = 当前预算 vs 知识库最低价
  - gpu_required: 二元约束，无法放宽（除非用户同意）
  - weight_max: 宽松度 = 当前重量上限 vs 知识库最轻独显本重量
  - ram_min: 宽松度 = 当前内存 vs 知识库常见配置
  - screen_size_range: 宽松度 = 当前范围 vs 知识库分布

按宽松度排序，找出"最容易通过放宽来恢复候选"的约束
```

### 7.2 冲突解释策略

不直接推荐违规商品，而是：

1. **说明冲突**："在您当前的条件下（预算<5000 + 必须独显），知识库中没有完全匹配的商品"
2. **分析原因**："因为带独立显卡的笔记本最低价格为 5499 元"
3. **给出选项**："您可以考虑以下调整：
   - 选项 A：将预算放宽到 5500 元以上
   - 选项 B：放弃独显要求，选择性能较强的核显轻薄本
   - 选项 C：降低其他要求（如接受更大重量）"
4. **等待用户决策**：用户选择后更新约束，重新过滤

### 7.3 冲突处理示例

```
用户："想要一台1kg以下、带RTX 4060、预算6000的游戏本"

Agent：
"我检查了知识库中的48款笔记本，没有找到同时满足这三项条件的商品。

冲突分析：
• 带 RTX 4060 的笔记本最轻为 2.1kg，无法满足 1kg 以下
• 带 RTX 4060 的笔记本最低价为 6499 元，超出您的预算

建议调整方案：
1. 放宽重量到 2.2kg 以内、预算到 6500 元 → 可以推荐拯救者 R7000 等
2. 放弃独显要求 → 可以推荐 1kg 以下的高性能轻薄本
3. 仅放宽重量 → 可以在预算内找到 2.0kg 左右的独显本

您希望调整哪项条件？"
```

## 八、工具调用设计

### 8.1 第一版 Agent 工具集

| 工具名 | 输入 | 输出 | 使用场景 |
|--------|------|------|----------|
| `parse_intent` | 用户输入文本/图片 | 意图类型 + 置信度 | 每次用户输入后调用 |
| `extract_constraints` | 用户输入 + 当前状态 | 硬约束 + 软偏好 + 缺失信息 | 意图为 purchase 时 |
| `ask_followup` | 缺失信息列表 | 追问文本 | 信息不足时 |
| `filter_products` | 硬约束 + 商品池 | 过滤后候选集 | 约束提取后 |
| `rank_candidates` | 候选集 + 软偏好 | Top-K 排序结果 | 过滤后 |
| `retrieve_evidence` | 候选 SKU + 查询 | 相关文本证据 | 生成推荐理由前 |
| `generate_comparison` | 2+ SKU | 对比分析文本 | 意图为 compare 时 |
| `generate_recommendation` | Top-K + 证据 + 约束 | 推荐理由文本 | 最终输出 |
| `check_facts` | 推荐理由 + 商品参数 | 事实校验报告 | 输出前 |
| `resolve_conflict` | 空候选集 + 约束 | 冲突分析 + 调整建议 | 过滤为空时 |
| `parse_image` | 图片 | 提取参数 + 匹配 SKU | 多模态输入时 |
| `update_state` | 新信息 | 更新后的 UserNeedState | 每轮对话后 |

### 8.2 工具调用决策逻辑

```
每次用户输入后的决策：

1. 调用 parse_intent
2. 根据意图类型：
   
   if intent == "purchase":
     → 调用 extract_constraints
     → 检查 missing_critical_info
       → if 有缺失 and 追问次数 < 1:
         → 调用 ask_followup → 等待回复
       → else:
         → 调用 filter_products
         → if 候选为空:
           → 调用 resolve_conflict → 等待用户决策
         → else:
           → 调用 rank_candidates
           → 调用 retrieve_evidence
           → 调用 generate_recommendation
           → 调用 check_facts
           → 流式输出结果
   
   elif intent == "compare":
     → 提取提及商品
     → 调用 generate_comparison
     → 流式输出
   
   elif intent == "inquiry":
     → 匹配 SKU
     → 调用 retrieve_evidence
     → 生成回答
     → 流式输出
   
   elif intent == "multimodal":
     → 调用 parse_image
     → 根据解析结果路由到 purchase/compare/inquiry
   
   elif intent == "clarify" or "resolve":
     → 调用 update_state
     → 重新进入 purchase 流程
```

## 九、流式输出设计

流式输出不是核心技术，但满足挑战赛要求并提升体验。

### 9.1 各阶段流式反馈

| 阶段 | 流式内容 | 目的 |
|------|----------|------|
| **意图识别后** | "正在理解您的需求..." | 确认输入已接收 |
| **约束提取后** | "已识别您的关键需求：预算8000元以内，需要独显，重量不超过2kg..." | 确认理解正确 |
| **过滤后** | "正在从48款商品中筛选..." | 展示处理进度 |
| **过滤为空时** | "没有找到完全匹配的商品，正在分析冲突..." | 提前告知异常 |
| **排序后** | "已为您找到5款符合条件的商品，正在生成对比..." | 预告输出规模 |
| **最终输出** | 逐步输出：候选列表 → 对比表 → 推荐理由 → 证据引用 | 渐进式呈现结果 |

### 9.2 流式实现要点

- 流式内容仅为状态提示和结果片段，**不流式暴露中间工具调用细节**
- 最终答案一次性结构化呈现（含对比表、推荐理由、证据来源）
- 如果发生约束冲突，流式输出冲突分析和选项

## 十一、关键设计决策确认

本方案已涵盖以下核心决策：

| 决策项 | 方案 | 说明 |
|--------|------|------|
| 约束提取 | LLM + 规则校验两层 | 保证提取准确性和边界安全 |
| 硬约束 | 7 个字段 | budget/gpu/ram/weight/screen/cpu/category |
| 软偏好 | 6 个维度 | performance/portability/battery/value/brand/scenario |
| 追问 | 最多 1 次，每次最多 2 个问题 | 轻量但有效 |
| 冲突处理 | 解释冲突 + 提供选项 + 等待决策 | 不违规推荐 |
| 排序 | 多维度加权融合 | 可解释、可调整 |
| 工具 | 12 个原子工具 | 覆盖完整流程 |
| 状态 | UserNeedState 结构 | 支持多轮和冲突恢复 |
| 流式 | 阶段提示 + 渐进输出 | 满足赛题要求 |

---

**请确认以下问题，确认后进入评估体系设计：**

1. **硬约束字段是否足够**？是否需要增加接口类型、屏幕类型等约束？
2. **追问次数限制**（1次）是否合理？是否需要增加到2次？
3. **冲突处理策略**是否可接受？是否需要在无满足结果时，主动推荐"最接近"的商品？
4. **工具粒度**是否合适？是否需要合并或拆分某些工具？
