# 第一版商品数据集方案 v0.2

**项目名称**：基于多模态 RAG 与约束推理的电商智能导购 Agent
**适用品类**：笔记本电脑（第一版）
**数据规模**：36–48 款具体 SKU
**更新日期**：2026-08-01

---

## 一、数据来源与核验流程

### 1.1 三层数据来源优先级

| 优先级 | 来源类型 | 用途 | 说明 |
|--------|----------|------|------|
| **1** | 品牌官方产品页/官方规格表 | CPU、GPU、内存、屏幕、重量、电池等**硬参数** | 信任度最高，优先采信 |
| **2** | 电商商品详情页 | 静态价格、商品标题、主图、详情页截图 | 采集时记录快照时间，不承诺实时有效性 |
| **3** | 专业评测/用户评论 | 卖点补充、体验描述、优缺点参考 | 文本证据来源，不用于结构参数 |

### 1.2 采集与核验流程

```
阶段 1：预选
  └── 从市场主流型号中预选候选 SKU（36–48 款）
  └── 记录预选清单（品牌、系列、目标配置）

阶段 2：官方数据采集（半自动）
  └── 访问品牌官方产品页或官方规格 PDF
  └── 使用辅助脚本提取参数表格（可选）
  └── 人工核对关键硬参数：CPU型号、GPU型号、内存容量、重量、屏幕规格

阶段 3：电商页面采集（半自动）
  └── 访问电商商品页（京东/天猫/官网商城）
  └── 采集：商品标题、静态价格、主图 URL、参数页截图
  └── 人工确认：价格、SKU 配置版本、图片完整性

阶段 4：文本知识收集
  └── 收集 1–3 条官方卖点文案
  └── 收集 1–2 条专业评测摘要（标明来源）
  └── 收集 3–5 条用户评论摘要（标明来源）

阶段 5：人工核验与入库
  └── 核验人逐条检查：硬参数是否与官方一致、SKU 配置是否唯一、价格是否记录
  └── 标注核验状态：已核验 / 部分核验 / 待核验
  └── 通过核验后写入 products.jsonl 和 documents.jsonl
```

### 1.3 核验要求

- 每条 SKU 的 **price / cpu_model / gpu_model / ram_gb / weight_kg / screen_size** 必须有至少一个独立来源交叉验证
- 电商页面的"多配置套餐"必须拆分为独立 SKU，不可混用参数
- 价格仅记录采集时的静态值，不追踪后续变动
- 数据写入后，核验人签名并标注核验日期

## 二、商品选择策略

### 2.1 数量与品牌

| 维度 | 要求 |
|------|------|
| 总 SKU 数 | 36–48 款 |
| 品牌数 | 6–8 个主流品牌 |
| 品类覆盖 | 轻薄本、全能本、游戏本三种类型 |

### 2.2 品牌建议池（第一版）

| 品牌 | 轻薄本 | 全能本 | 游戏本 |
|------|--------|--------|--------|
| 联想 | ThinkPad X1 / 小新 Pro | YOGA Pro / ThinkBook | 拯救者 Y7000P / R7000 |
| 华硕 | 灵耀 14 / 无畏 Pro | ProArt 创 16 | 天选 5 / ROG 魔霸 |
| 惠普 | 战 66 / 星 Book Pro | 暗影精灵 Slim | 暗影精灵 10 |
| 苹果 | MacBook Air / Pro | MacBook Pro | — |
| 华为 | MateBook 14 / X Pro | — | — |
| 戴尔 | XPS 13 / 灵越 14 Plus | 灵越 16 Plus | — |

### 2.3 价位段分布（确保同价位可比性）

| 价位段 | 目标数量 | 说明 |
|--------|----------|------|
| 3000–5000 元 | 8–12 款 | 轻薄本为主，少量入门全能本 |
| 5000–8000 元 | 12–16 款 | 轻薄本/全能本/游戏本均有分布 |
| 8000–12000 元 | 8–12 款 | 中高端游戏本、创作本 |
| 12000 元以上 | 4–8 款 | 旗舰轻薄本、旗舰游戏本 |

### 2.4 选择原则

1. **同价位可比**：每个价位段至少保留 3–5 款可互相替代的商品
2. **同场景可替代**：同类型（如轻薄本）中，至少 2–3 款满足相近预算和性能
3. **硬参数覆盖全面**：确保每种硬约束组合（预算+重量+内存+独显）都有匹配对象
4. **发布时间集中**：优先 2024–2026 年上市机型，减少因代际差异造成的参数失真
5. **不追新**：不收录刚发布、参数未稳定的机型

## 四、文本证据与派生总结的区分

这是评估客观性的关键。所有文本内容分为三类，在 documents.jsonl 中必须标注 type 字段。

### 4.1 三类文本内容

| 类型 | 标识 | 内容特征 | 来源要求 | 可信度 | 用途 |
|------|------|----------|----------|--------|------|
| **客观事实** | `fact` | 可验证的参数、规格、保修条款 | 品牌官网/官方规格表 | **高** | 事实校验的标准答案 |
| **有来源的文本证据** | `evidence` | 官方卖点、评测片段、用户评论摘要 | 必须标明来源和采集日期 | **中** | RAG 检索语料，推荐理由的证据来源 |
| **派生总结** | `derived` | 场景描述、优缺点总结、评论综合 | 由人工或模型生成 | **低（需验证）** | 展示和生成参考，**不作为事实校验依据** |

### 4.2 在 documents.jsonl 中的记录格式

```jsonl
{
  "sku_id": "lnv_y7p_2024_i7_4060_32",
  "document_type": "fact",
  "source": "联想官网产品页",
  "source_date": "2026-07-15",
  "content": "CPU: Intel Core i7-14650HX, 16核24线程, 最高睿频5.2GHz"
}
{
  "sku_id": "lnv_y7p_2024_i7_4060_32",
  "document_type": "evidence",
  "source": "什么值得买评测",
  "source_date": "2026-03-20",
  "content": "拯救者Y7000P 2024在《赛博朋克2077》高画质下平均帧率82fps，散热表现稳定"
}
{
  "sku_id": "lnv_y7p_2024_i7_4060_32",
  "document_type": "derived",
  "source": "人工总结",
  "source_date": "2026-07-31",
  "content": "适合游戏玩家、编程开发、视频剪辑等高性能需求场景"
}
```

### 4.3 避免闭环自证的原则

- **派生总结不得作为事实校验的标准答案**。例如：如果 pros_summary 说"屏幕素质优秀"，系统推荐理由中复述了这句话，这不计入"参数事实准确率"
- **事实准确率只校验结构化字段和客观事实**。例如：系统说"这款搭载 RTX 4060"，校验 gpu_model 字段是否为 RTX 4060
- **证据忠实度评估时**，检查推荐理由是否引用了真实存在的 evidence 或 fact，而非自己编造或循环引用派生总结

## 五、多模态数据的具体用途

### 5.1 第一版多模态能力定位

**不做**：
- 商品外观图片相似度检索
- 图像生成或图像编辑
- 视频解析

**做**：
- 用户上传商品详情页截图或参数表截图 → 多模态模型提取品牌、型号、价格和主要参数 → 与知识库 SKU 匹配 → 进入咨询/对比/推荐

### 5.2 具体流程

```
用户上传图片
  → 多模态 LLM（如 GPT-4V / Claude 3）解析图片
  → 提取文本：品牌、型号、价格、关键参数
  → 参数规范化（与结构化字段对齐）
  → 与 products.jsonl 中的 SKU 做匹配
  → 返回匹配到的 SKU 列表
  → 用户可选择进入：单商品咨询 / 多商品对比 / 基于该商品推荐相似款
```

### 5.3 图片资源清单（每款 SKU）

| 图片 | 数量 | 用途 | 要求 |
|------|------|------|------|
| 商品主图 | 1 张 | 展示、结果呈现 | 清晰、无水印、正面外观 |
| 参数页截图 | 1 张 | 多模态解析、事实校验 | 包含主要参数表格 |
| 关键详情图 | 0–1 张 | 展示补充 | 接口图、散热图等（可选） |

## 六、最终目录结构

```
data/
├── products.jsonl              # 结构化商品记录（36–48 条）
├── documents.jsonl             # RAG 文本语料（多条/每 SKU）
├── images/
│   └── <sku_id>/
│       ├── main.jpg            # 商品主图
│       ├── param_page.png      # 参数页截图
│       └── detail.jpg          # 关键详情图（可选）
├── schemas/
│   ├── product_schema.json     # products.jsonl 字段定义与约束规则
│   └── document_schema.json    # documents.jsonl 字段定义
└── evaluation/
    ├── queries.jsonl           # 测试查询集（60–100 条）
    ├── annotations.jsonl       # 人工标注（期望商品、约束、不应推荐）
    └── experiment_results/     # 各基线实验结果
```

### 6.1 文件说明

| 文件 | 内容 | 维护方式 |
|------|------|----------|
| `products.jsonl` | 每款 SKU 的结构化参数和元数据 | 人工录入+核验 |
| `documents.jsonl` | RAG 检索语料，每条含 sku_id + document_type + source + content | 人工整理+可选自动生成 |
| `images/<sku_id>/` | 该 SKU 的图片资源 | 下载/截图后人工命名 |
| `schemas/*.json` | 字段定义、类型约束、验证规则 | 一次定义，后续按 schema 校验 |
| `evaluation/queries.jsonl` | 测试查询，含查询类型、自然语言查询、预期行为 | 人工设计+半自动生成 |
| `evaluation/annotations.jsonl` | 标注结果，含硬约束、允许商品集合、禁止商品、是否应追问 | 人工标注 |

### 6.2 向量索引的构建

向量索引**不由手动维护文件**，而是由程序在初始化阶段自动构建：

```
启动时加载
  ├── 读取 documents.jsonl
  ├── 按 document_type 过滤（仅 fact + evidence 进入向量库，derived 可选）
  ├── 使用 Embedding 模型编码 content
  ├── 构建向量索引（如 FAISS / Milvus Lite / Chroma）
  └── 持久化索引文件（如 faiss_index.bin）
```

## 七、数据采集与质量检查清单

### 7.1 SKU 去重与版本区分规则

| 检查项 | 规则 | 通过标准 |
|--------|------|----------|
| SKU 粒度 | 以具体配置版本为单位 | 同品牌+同系列+同CPU+同GPU+同内存+同存储 = 同一 SKU |
| 存储差异 | 512GB 与 1TB 版本 | 可保留两条，model_name 必须明确标注存储容量 |
| 命名规范 | `品牌_系列_年份_CPU_GPU_内存` | 例如：`lnv_y7p_2024_i7_4060_32` |
| 映射表 | 维护 series → SKU 列表 | 一个系列可能对应多个 SKU |

### 7.2 参数一致性校验清单

每款 SKU 入库前必须检查：

- [ ] `price` 为整数，单位元，范围 2000–30000
- [ ] `weight_kg` 精确到小数点后两位，范围 0.80–4.00
- [ ] `gpu_type` 只能是 **"独立显卡"** 或 **"核显"**
- [ ] `ram_gb` 为常见值（8/16/32/64），单位 GB
- [ ] `screen_size` 为常见值（13.3/14.0/15.6/16.0/17.3），单位英寸
- [ ] `product_category` 只能是 **"轻薄本" / "全能本" / "游戏本"**
- [ ] `verification_status` 为 **"已核验"** 时才可用于测试和演示
- [ ] 至少有一个 `data_sources` 为品牌官方来源

### 7.3 截图关联校验

- [ ] 每款 SKU 的 `image_main` 存在且可读取
- [ ] `image_param_page` 存在且可读取
- [ ] 截图中的参数与结构化字段无冲突（抽检 20%）

### 7.4 来源标注要求

- [ ] 每条客观事实必须标注来源和日期
- [ ] 每条证据必须标注来源和日期
- [ ] 派生总结必须标注"人工总结"或"模型生成"及日期
- [ ] 禁止未标注来源的文本进入 documents.jsonl

### 7.5 评估数据准备要求

测试集查询设计必须覆盖以下类型：

| 查询类型 | 数量建议 | 示例 |
|----------|----------|------|
| 正常购买需求 | 20–30 条 | "推荐一款适合编程的笔记本，预算7000左右" |
| 硬约束查询 | 15–20 条 | "必须带独显，重量不超过1.5kg，预算8000以内" |
| 多条件组合 | 10–15 条 | "16寸屏、32GB内存、RTX4060、预算1万以内" |
| 模糊需求（应追问） | 5–10 条 | "我想买个好点的笔记本" |
| 无完全满足结果（冲突） | 5–10 条 | "重量<1kg + RTX4090 + 预算<5000" |
| 商品对比查询 | 5–10 条 | "联想拯救者Y7000P和华硕天选5怎么选" |
| 多模态查询 | 5–10 条 | [上传参数截图] + "这款值得买吗" |

每条测试查询标注字段：
- `query_type`：查询类型
- `hard_constraints`：提取出的硬约束（JSON）
- `allowed_skus`：允许的相关商品集合（列表）
- `forbidden_skus`：明确不应推荐的商品（列表）
- `should_ask_followup`：是否应当追问（布尔）
- `no_exact_match`：是否无完全满足结果（布尔）

**本方案确认后，进入下一个关键决策：约束推理与 Agent 分支设计。**
